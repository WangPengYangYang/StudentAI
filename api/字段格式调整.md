# JSON 字段命名统一为 snake_case —— 前端对接改动文档

> 版本：v1.0（2026-08-04）
> 背景：后端统一对外 API JSON 字段为 snake_case（与项目 ~80% 现状、NexusAgent/微信生态对齐）。已与前端达成一致，前端配合调整。
> 时序：**两批发布**。批次 A（兼容期）后端先行上线，**不破坏现有前端**；批次 B（切换期）前端按本文档切换。

---

## 1. 发布时序

```
批次 A（后端发布，无前端配合要求）
  ├─ 后端结构体双兼容读取（新写 snake_case，旧数据 camelCase 仍可读）
  ├─ 新写入数据 = snake_case
  └─ 前端无需改动（旧字段仍可用）

批次 B（前端 + 后端协同切换）
  ├─ 前端按本文档映射表改字段名
  ├─ 后端执行存量数据迁移（3 列 JSON）
  ├─ Agent 契约确认
  └─ 前端切换完成后后端清理兼容代码
```

**前端配合窗口**：批次 B。届时前端所有接口的 camelCase 字段名需按下表改为 snake_case。

## 5. 兼容期保障（批次 A）

- 批次 A 期间，**旧 camelCase 字段仍返回**（后端双兼容：写 snake、读兼容双格式），前端可零改动运行
- 若前端希望提前适配，可在批次 A 期间分接口渐进切换（后端同时输出两种格式的场景下，以本文档映射表为准）
- 注意：**同一响应体内不会同时出现两个字段名**（如 `school_id` 与 `schoolId` 不同时返回；批次 A 兼容期读取用双解析但响应输出以新 snake_case 为准，前端需按新字段消费）

> ⚠️ 修正：批次 A 对外响应即输出 snake_case（读取兼容仅针对存量 DB 数据）。因此**前端切换可在批次 A 后立即开始**，无需等批次 B。

## 7. 回滚方案

- **批次 A**：后端回滚需附带 **snake→camelCase 数据回切脚本**——批次 A 新写入的 DB JSON 为 snake_case，仅回滚代码会导致旧代码（camelCase 读取）读不回批次 A 期间产生的新数据；执行顺序：先跑数据回切脚本 → 再回滚代码
- **批次 B**：迁移前对 3 列 JSON 备份；异常时恢复备份 + 前端回切 camelCase
- 前端回滚：切换代码保留在版本控制，必要时 revert
